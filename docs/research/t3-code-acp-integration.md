# What Automagik can learn from T3 Code's ACP integration

November 26, 2026 · Automagik `2d483a66215e6986d6b1c2296c9f268c8c26d202` (matched remote `dev`) · T3 Code `0b6b173244314899ff1a26524e56994adce88c8d` (public `main` at inspection).

**Recommendation.** Start with one replayable conversation that checks both the ACP messages and the chat a person can reopen. Use it to deliver same-agent restart continuity on one proven route. The next visible improvement should be preserving an agent's plan through streaming, completion and reopening. Keep DSH responsible for chat history, Bot identity and tool approval.

## Delivery plan

### 1. Make one round trip reproducible

Extend the existing ACP fake and desktop log reader tests. Start with a synthetic Claude-style bridged turn. A person asks for a tool action, approves once, sees one result, closes the chat and reopens it. Describe the exchange as expected outbound requests, inbound responses/updates, and expected DSH rows. Verify the outbound permission option, tool ID, result, stop reason and reopened row sequence. Mutating a frame or duplicating a result should fail the fixture. Add variants for Stop while approval is open and an auth-required handshake. Automagik already has independent assertions for withdrawn approvals, ignored cancellation and old log recovery. [Permission handling](../../apps/acp-dsh/src/host/acp.js#L1260) · [Stop and reap](../../apps/acp-dsh/src/host/adapter.js#L1214) · [Reader regressions](../../apps/desktop/test/acp-bridge-tool-lifecycle-independent.test.js#L241) · [ACP cancellation contract](https://agentclientprotocol.com/protocol/v1/prompt-turn#cancellation)

Extend the drift job to consume a receipt from the process that launched each adapter. Record SDK, adapter, CLI, platform, scenario and phase reached. Label synthetic replay, real signed-out handshake and signed-in turn distinctly. A real signed-out pass must leave prompt, tool approval, recovery and usage unverified. Start with synthetic fixtures and Automagik's existing sanitized examples. Derive any later recorded fixture from a designated test conversation, with allowlisted fields and stable placeholder IDs. Keep ordinary diagnostics to methods, timing, counts and error classes. [Current CI](../../.github/workflows/acp-drift.yml) · [Existing permission fixtures](../../apps/acp-dsh/test/permission-payloads.test.js#L16)

### 2. Prove restart continuity, then enable it per route

Pilot an explicit same-agent, same-Bot, same-workspace restart. First measure whether the installed connector can reattach the native session **and** bind a fresh bridge with today's tools and approvals. This is the release decision. RFC 0003 calls for native load, but also documents Codex ignoring a replacement MCP server list on resume. An advertised capability alone cannot qualify a bridged route. Test Claude and Codex independently. Start rollout with whichever passes. [Resume intent](../rfcs/0003-model-routes-and-acp.md#L109) · [Known bridge constraint](../rfcs/0003-model-routes-and-acp.md#L411)

- Persist an opaque native ID with the DSH session, account/home generation, workspace, Bot identity and policy compatibility information. Revalidate these against the current session before reattachment. Mint a fresh bridge credential. An old record without a binding takes the existing path. [Account binding](../../apps/acp-dsh/src/host/consent.js#L5) · [Current replay behavior](../rfcs/0003-model-routes-and-acp.md#L472)
- Prefer advertised resume when DSH already has the complete visible history. Where only load is supported, consume history in a replay-only phase. Historical tool calls must never execute, open approval dialogs or append duplicate rows. Keep another live session's updates flowing. If a connector cannot safely restore the tool set, keep its current fresh-session path and existing replay setting.
- **Acceptance.** On a qualifying route, a synthetic agent remembers a marker held only in its native context across host restart. The original tool credential is unusable, a removed tool stays unavailable, and a newly offered tool produces exactly one approval and one result. Also cover stale native ID, changed account, changed Bot identity or permissions, an old chat without a binding, and Stop during recovery. A failure after prompt dispatch must never automatically resend a possibly executed action. Cross-harness Bot handoff keeps its existing contract. [Current handoff behavior](../rfcs/0030-code-mode-in-the-app.md#L325)
- **Rollout and measurement.** Enable per connector/version after the isolated real-adapter scenario confirms it. Compare native reattachments, fresh-session fallbacks by reason, bytes of DSH history sent, duplicate rows, and time from reopen to first agent output on the same fixture. Turning the route off should immediately restore the existing restart behavior.

### 3. Give the chat one more reliable event

Start with the agent's plan. Inventory the valid plan shapes accepted by the pinned SDK. Map create/update/remove into one DSH-owned plan presentation, retaining its ID and position across updates and reload. Check the desktop log reader and the Bot chat before choosing a persisted row type. A test already distinguishes a schema-rejected legacy plan from a valid update the integration elects to ignore. Treat both conditions explicitly in diagnostics. The slice passes when a multi-update plan stays in place, reopening reconstructs the same state, an unsupported update leaves later text and the final response intact, and old logs still open. [SDK boundary](../../apps/acp-dsh/test/sdk-2-7-surface.test.js#L144) · [Existing upstream chat-row design](../rfcs/0023-dsh-upstream-agent-context-and-chat-rows.md#L99)

If token usage is also wanted in chat, follow with a separate slice. Verify each route's semantics for context occupancy, per-prompt tokens, cache and interrupted prompts. Preserve provenance and represent missing data as unknown. A replay or reconnect must never charge the same prompt twice. Any durable cost or attribution calculation belongs to the existing meter contract. [T3 per-prompt handling](https://github.com/pingdotgg/t3code/blob/0b6b173244314899ff1a26524e56994adce88c8d/packages/provider-acp/src/server/adapter.ts#L370) · [Automagik meter ownership](../rfcs/0018-meter-query-contract.md#L24)

### When to consider a native Codex driver

After the replay suite exists, run the same restart, approval, Stop and model-change scenarios through Automagik ACP and T3's native Codex path using equivalent model, account policy and workspace. Measure time to first output, retained context and visible failures. A native-driver proposal is justified if an important, repeatable gap survives the ACP improvements and can be attributed to the transport. Such a proposal would need to preserve public route IDs, DSH-owned tool approvals and saved chats. [Public route contract](../rfcs/0003-model-routes-and-acp.md#L30) · [T3 Codex transport](https://github.com/pingdotgg/t3code/blob/0b6b173244314899ff1a26524e56994adce88c8d/apps/server/src/orchestration-v2/Adapters/CodexAdapterV2.ts#L1994)

The desktop loader regression file ran through the same wrapper and passed all three tests, covering old-log recovery, orphan results and repeated call IDs. [Offline check](../../apps/acp-dsh/scripts/acp-drift.mjs#L102) · [Desktop test](../../apps/desktop/test/acp-bridge-tool-lifecycle-independent.test.js#L241)

Which signed-in connector can reconnect with a fresh bridge, which plan or usage fields each deployed version actually emits, and which behavior accounts for the perceived quality difference remain open. This comparison used public implementation, local source, the current T3 driver identity, and the two offline checks. It did not capture a signed-in conversation, start a service, run a full suite or measure comparative latency.
